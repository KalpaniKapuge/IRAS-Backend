#C CHAPTER 07 - CONCLUDING REMARKS

# 7.1 Accomplishment of the Research Objectives

Each research objective set out in Section 1.7 is revisited here against triangulated evidence drawn from the literature review (Chapter 2), the implemented system (Chapter 5), and the testing and evaluation carried out in Chapter 6, rather than against a single source of proof.

**To identify** the primary challenges of conventional and AI-based recruitment processes was accomplished in Section 1.2 and Section 2.4: shallow keyword-based screening, fragmented single-purpose AI tools, absent candidate feedback, and low auditability of AI-influenced decisions were each identified from the problem background and confirmed independently against twenty-eight literature sources in Chapter 2, giving this objective two independent lines of supporting evidence rather than one.

**To analyze** the existing state of recruitment automation systems, algorithms, and technologies was accomplished through Section 2.5's algorithmic, design, and workflow analysis, and cross-checked in Section 4.3's operationalization table, which traces every resulting requirement back to a specific gap identified during that analysis — no requirement in Table 4.5 or Table 4.6 was introduced without a corresponding entry in that trace.

**To design / implement / develop** a web-based Intelligent Recruitment Automation System with Candidate, Employer, and Admin modules was accomplished and is evidenced directly by the implemented architecture (Section 4.5), the twenty-one functional requirements realized in the services and controllers described in Chapter 5 (Section 5.2 in particular), and the seven use cases specified in Section 4.4.1.

**To evaluate** the system against matching accuracy, ranking relevance, skill-gap identification, CV-generation correctness, usability, and transparency was **partially accomplished**. The matching-accuracy strand of this objective is fully evidenced: the deployed candidate-job fit classifier — XGBoost, the highest-scoring configuration of the four algorithms compared (Section 6.4) — was evaluated empirically to 98.9% test accuracy, and the underlying scoring algorithm was traced end to end against its ten specified test cases (Section 6.2). The usability and CV-generation-correctness strands, which depend on a deployed instance being exercised by real candidates and employers, remain open and are carried forward explicitly as future work in Section 7.5 rather than being claimed as complete.

Triangulating across these four objectives, three were fully accomplished with corroborating evidence from at least two independent chapters, and the fourth was accomplished for its quantitative (matching-accuracy) component while its human-evaluation component is scoped as near-term future work — an honest, rather than inflated, account of where this research currently stands.

# 7.2 Problems Encountered

Several concrete problems were encountered during this research, each of which shaped a design or process decision rather than being merely incidental.

The most significant technical problem was the **cross-platform model serialization failure** described in Section 6.4: a model trained in a cloud Linux environment could not be loaded in the Windows deployment environment despite identical library versions, which — before it was resolved — forced an interim choice of Logistic Regression over the higher-scoring XGBoost model for production use. The eventual fix — exporting the XGBoost booster through its own native, OS-independent format rather than joblib-pickling it as part of a single combined artifact — meant XGBoost could still be deployed after all, without the accuracy trade-off the failure had first appeared to force. The problem nonetheless generalized into a design principle applied elsewhere in the system: prefer a component's own portable, self-describing serialization format over a generic pickle-based one whenever a compiled, environment-specific structure is involved — Table 5.1's technology choices elsewhere in the stack (JWT claims, JSON DTOs, relational rows) already favoured plain, portable state for the same underlying reason.

A second problem, discovered during this evaluation rather than anticipated in advance, was the **compile-time interface drift** in the existing xUnit test project (Section 6.3): the hand-written FakeScoringService no longer implements the current IScoringService interface, after that interface was extended to support per-candidate proactive job recommendations. This is recorded as an immediate follow-up: the fake's missing ComputeMatchSignalsForCandidateAsync method must be implemented before the automated test suite can run again, and it should be revisited early in the next development cycle so the suite does not remain silently unusable.

A third problem was **data availability**. Real recruitment data — actual candidate resumes, real employer hiring decisions — is exactly the sensitive category of information Table 3.2 identifies as an ethical risk, so it could not be used directly even where it might have improved the fit-classifier's training signal. The classifier in Chapter 6 was instead trained on synthetic and publicly available candidate-job pairs, consistent with the fact-collection strategy set out in Section 3.4; this is methodologically defensible and ethically necessary, but it does mean the 98.5% test accuracy reported in Section 6.4 should be read as evidence that the modelling approach works on data of this kind, not yet as a guarantee of the same accuracy against the messier, more varied resumes a production deployment would eventually see.

A fourth, more structural problem was that the AI microservice depends on a separate Python codebase maintained outside the ASP.NET Core solution documented in this thesis (Section 4.5's deployment note). This created a recurring documentation risk — several implementation details in Chapter 5 (the exact embedding model, the exact classifier library) could only be described at the level the .NET-side HTTP contract (IAiServiceClient) exposes, rather than confirmed against the Python service's own source, since that service falls outside this thesis's repository boundary.

# 7.3 Self-Reflection

## 7.3.1 Ideology About the Research Carried Out

This research was approached with the conviction that AI-assisted automation is only valuable in a recruitment context if it remains auditable by the humans it affects. That conviction shaped concrete choices throughout the system rather than remaining an abstract principle: the weighted scoring formula (Section 5.1.1) exposes every signal it combines rather than returning an opaque score; AI-generated job descriptions and evidence-review decisions both pass through an explicit human-approval or confidence-gated step (Section 5.2) rather than acting unsupervised; and every AI-influenced action is written to an audit log (NFR-09). The research therefore treats "AI-assisted" and "AI-automated" as meaningfully different design goals, and consistently chose the former.

## 7.3.2 Benefits Gained

This research produced concrete benefit beyond the artifact itself. It required combining skills that are rarely exercised together in a single undergraduate project — backend API design, a trained classifier's practical deployment constraints, prompt-based LLM integration with a deterministic fallback, and requirements traceability discipline (Section 4.3) — which gave a realistic picture of how a production-oriented AI feature differs from a notebook experiment. It also produced a durable, reusable evaluation method: the operationalization table in Section 4.3 and the requirement-to-test-case trace in Section 6.2 are patterns that can be reapplied to any future feature added to the system, not just the ones documented in this thesis.

## 7.3.3 Learning Curves

Three learning curves stood out. The first was operational rather than algorithmic: understanding why a model that scores well in a notebook can fail entirely in production (the XGBoost cross-platform issue) required learning about serialization formats and deployment environments, not about machine learning theory. The second was architectural: deciding where to draw the service boundary between the .NET backend and the Python AI service (Section 4.5) required weighing failure isolation and technology fit against the added latency and operational complexity of a second deployable unit. The third was disciplinary: maintaining the traceability chain from research objective, through requirement, through implementation, to test case (Sections 4.3 and 6.2) took considerably more sustained rigor than writing the corresponding code, and is the discipline most likely to be under-practised in a time-constrained undergraduate project.

# 7.4 Business Insight of the Idea

## 7.4.1 Real-World Application Possibilities

IRAS's core contribution — a multi-signal, explainable match score combined with a closed skill-gap-to-evidence loop — has application value beyond the IT and Software Engineering scope defined in Section 1.10. The same architecture (taxonomy-based skill matching plus semantic similarity plus a trainable fit-classifier) generalizes to any domain with a definable skill taxonomy, such as healthcare credentialing, technical trades, or professional certification tracking, by substituting the taxonomy and retraining the classifier rather than redesigning the scoring pipeline itself.

For a recruitment agency or an in-house talent-acquisition team specifically, the most commercially relevant capability demonstrated in this thesis is not the LLM-generated text (job descriptions, feedback, chatbot replies), which is now a commodity capability offered by many vendors, but the **auditable scoring and evidence-review pipeline** (Sections 5.1.1 and 5.2): a defensible, explainable match score is a genuine differentiator in a market where, as noted in Section 1.2, AI-driven resume screening is already widespread but frequently opaque. A viable commercialization path would package the scoring engine and skill-gap/evidence-review workflow as a white-label module that an existing ATS vendor could integrate, rather than competing as a full end-to-end platform against incumbents.

# 7.5 Future Recommendations

Based on the problems encountered (Section 7.2) and the objective accomplishment gaps (Section 7.1), the following recommendations are made for continuing this research beyond this thesis. They are ordered roughly by dependency: the first two are prerequisites for producing trustworthy evidence at all, the middle three extend the system's existing capability, and the last tests how far the underlying approach generalizes beyond its current scope.

- Restore the xUnit test suite to a compiling, executable state by implementing the missing IScoringService member on FakeScoringService, then re-run and report the full suite's pass/fail results as a supplement to this thesis's evaluation.
- Conduct the usability and CV-generation-correctness evaluation against a deployed instance with real candidate and employer participants, closing the evaluation gap identified in Section 7.1.
- Conduct load/performance testing against NFR-01 and NFR-10 under realistic concurrent request volume, since this thesis's evaluation window did not include a deployed instance under load.
- Enable the ML Fit Score and Assessment Score weights in ScoringOptions (both default to zero, Section 5.1.1) in a controlled rollout, and measure whether the now-deployed XGBoost classifier improves ranking quality over the skill-and-semantic-only baseline in production, not only on the offline held-out test set.
- Generalize the native, per-library serialization workaround used to unblock XGBoost (Section 6.4) into a single, format-independent deployment path for tree-ensemble models — for example, exporting to ONNX — so that a future model choice is not exposed to the same cross-platform risk purely because a different library's native format was not yet handled.
- Extend the skill taxonomy and retrain the fit-classifier for at least one additional domain beyond IT and Software Engineering, as a first empirical test of the generalization claim made in Section 7.4.1.

# 7.6 Chapter Summary

This concluding chapter assessed the research objectives set out in Chapter 1 against triangulated evidence from the literature review, the implementation, and the testing and evaluation chapters, finding three objectives fully accomplished and the fourth accomplished for its quantitative component with its human-evaluation component carried forward as near-term future work. It documented the technical and process problems encountered — most significantly the cross-platform model-serialization failure and the compile-time test-fake drift discovered during evaluation — reflected on the research ideology, benefits, and learning curves involved, considered the business and real-world application potential of the system's core scoring and evidence-review contribution beyond its current IT-recruitment scope, and set out six concrete recommendations for continuing this work. Taken together with Chapters 1 through 6, this thesis has presented the complete design, development, and evaluation cycle of the Intelligent Recruitment Automation System.
