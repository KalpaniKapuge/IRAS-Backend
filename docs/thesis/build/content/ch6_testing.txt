#C CHAPTER 06 - TESTING AND EVALUATION

# 6.1 Chapter Overview

This chapter evaluates IRAS against the functional and non-functional requirements specified in Section 4.6. Three complementary layers of evidence are used. First, the trained candidate-job fit classifier — the machine-learning contribution described in Section 5.1.1's ML Fit Score signal — is evaluated empirically on a held-out test set, since this is the one component of the system for which numeric ground truth exists. Second, the backend's existing automated test suite (IRAS.Tests, built on xUnit) was executed as part of this evaluation. Third, a design-time functional and non-functional test plan traces each requirement in Table 4.5 and Table 4.6 to the implementation described in Chapter 5. The chapter concludes with a review of the testing strategies used and their suitability to a research prototype of this kind.

# 6.3 Testing / Evaluation Workflow

Three evidence sources were combined for this chapter, in increasing order of how directly they were executed during this evaluation:

1) **Design-time traceability** (Tables 6.1 and 6.2): every test case cites the exact requirement it verifies and the exact implementation unit responsible, so that a reviewer can re-derive the expected result from the source code in Chapter 5 without needing a running deployment.

2) **The existing automated test suite.** IRAS.Tests (xUnit) was executed against the current codebase as part of this evaluation. The run did not reach any test execution: the compiler rejected the build with `CS0535 — 'FakeScoringService' does not implement interface member 'IScoringService.ComputeMatchSignalsForCandidateAsync(...)'`. This is a genuine, currently open defect in the test project — the IScoringService interface was extended (Section 5.1.1, Algorithm 3's per-candidate recommendation path) after the hand-written fake in IRAS.Tests/Support/Fakes.cs was last updated, and the fake was never brought back into conformance. This is reported here rather than silently fixed, because it is itself useful evaluation evidence: it demonstrates, concretely, why a statically typed backend was selected in Table 5.1 — the mismatch was caught at compile time, before a single test could run against a stale fake and produce a misleadingly green build. Bringing IRAS.Tests/Support/Fakes.cs back into conformance with IScoringService is recorded as an immediate follow-up action in Section 7.2.

3) **Empirical evaluation of the trained fit-classifier**, presented in full in Section 6.4 below, which is the one part of the system for which this thesis has complete, executed, numeric results.

# 6.4 Review of Test Strategies Used

Not every testing strategy commonly associated with a machine-learning-backed web platform is equally applicable to IRAS at its current stage, and each choice below is justified against the nature of the specific component being evaluated rather than applied uniformly.

**Model training and held-out test evaluation** was used for the candidate-job fit classifier because it is the one component with objective ground truth (labelled candidate-job pairs) against which accuracy can be measured numerically, unlike the LLM-generated text features (job descriptions, feedback, chatbot replies) which are evaluated qualitatively instead (Section 2.5.1, tenth algorithmic approach).

Four algorithms — Logistic Regression, Random Forest, Linear SVM, and XGBoost — were trained and compared under two input configurations to isolate the contribution of the engineered, structured features (skill overlap and semantic similarity) from the free-text signal alone.

**Best model selection.** Although XGBoost scored highest on the held-out test set, deploying it initially proved non-trivial. During integration testing, the XGBoost model trained in a cloud Linux environment (Google Colab) failed to deserialize on the Windows-based local deployment environment — even with identical XGBoost library versions (3.4.1) confirmed on both sides — when the trained pipeline was joblib-pickled as a single artifact; the load failed with a corrupted input stream. A version mismatch and file-transfer corruption were both tested and ruled out (by checking the version immediately before saving, and by successfully re-saving and re-loading the model within the same environment), isolating the cause to a known limitation of XGBoost's compiled, native gradient-boosted-tree structure not round-tripping cleanly through joblib's pickle protocol across operating systems. Logistic Regression, Random Forest, and Linear SVM carry no such risk, since their trained parameters are plain Python/NumPy arrays rather than a compiled native structure, and — with the accuracy gap to XGBoost only 0.4 percentage points (98.5% vs. 98.9%), both comfortably above the 80% target — Logistic Regression was deployed as an interim production model on that basis, favouring deployment reliability over a marginal accuracy gain.

This was not treated as a closed question. The scikit-learn preprocessor (the `ColumnTransformer` handling the structured and text features) has no such portability problem — it is plain Python/NumPy state and pickles safely with joblib — so the fix was to stop bundling the XGBoost booster inside that same joblib artifact and instead export it separately through its own native, OS-independent `save_model()`/`load_model()` JSON format, which does not depend on Python's pickle protocol at all. With the preprocessor and the booster loaded as two separate artifacts rather than one joblib-pickled pipeline, the cross-platform failure did not recur, and **XGBoost is the model actually deployed to production**, reaching 98.8% macro F1-score with a No Fit F1-score of 98.5%, a Potential Fit F1-score of 98.0%, and a Good Fit F1-score of 100% on the holdout set — the highest-scoring configuration of the four algorithms compared, deployed without the accuracy trade-off the initial serialization failure had first appeared to force.

**Discrimination quality (ROC and precision-recall).** Beyond the point estimates in Table 6.5, the best-scoring model's ranking quality was also examined threshold-independently.

FIGPEND:roc_pr_xgboost.png|Figure 6.3|ROC and Precision-Recall Curves — XGBoost (Full-Feature). The one-vs-rest ROC curves reach an AUC of 0.998 for No Fit, 0.997 for Potential Fit, and 1.000 for Good Fit, and the corresponding precision-recall curves reach an average precision of 0.997, 0.988, and 1.000 respectively — confirming that even the one class every model struggles with most at a fixed decision threshold (Potential Fit, Table 6.8) is still separated near-perfectly once the full range of thresholds is considered, and that the earlier point-estimate weakness is a threshold-calibration matter rather than a sign the model cannot discriminate that class at all.

**Learning curves and overfitting behaviour.** Training-set-size sweeps were run for both feature configurations to check whether the models had converged or were still data-starved, and whether the gap between full-feature and text-only performance (Figure 6.1) was a feature-quality problem or simply a case of the text-only models needing more data.

FIGPEND:learning_curves_textonly.png|Figure 6.4|Learning Curves — Text-Only Feature Set (Accuracy and Log Loss vs. Training Set Size). For all four algorithms, validation accuracy rises only modestly across the training-size sweep (from roughly 0.42-0.47 up to 0.50-0.63) and stays well below the 0.8 target even at the largest training size tested, while Random Forest and XGBoost's training accuracy sits pinned near 1.0 throughout — the classic signature of overfitting to the training folds rather than of a model that would keep improving with more text-only data. Logistic Regression and linear SVM show the opposite pattern, with training accuracy itself declining as more data is added (a sign the linear decision boundary is already underfitting the text-only feature space, not just failing to generalize it). Read together with Figure 6.1, this indicates the full-vs-text-only accuracy gap is a feature-quality ceiling, not a data-quantity shortfall — more resumes would not close it; more structured features would.

**Validation-estimate reliability.** Cross-validation accuracy during model selection was checked against the untouched holdout test set to confirm the validation folds were not systematically optimistic.

FIGPEND:validation_vs_holdout.png|Figure 6.5|Cross-Validation Accuracy vs. Untouched Holdout Test Accuracy, by Model and Feature Set. For every full-feature model, holdout test accuracy lands within, or just above, the cross-validation estimate's error bars (XGBoost, Logistic Regression, and SVM cluster tightly around 0.98-0.99 on both axes; Random Forest's holdout accuracy of 0.93 exceeds its own, wider CV estimate), indicating the validation folds were not optimistic and Table 6.5's holdout numbers are a trustworthy estimate of production performance rather than an artefact of a favourable train/test split. The text-only models show the same non-optimistic pattern but with visibly larger error bars — the weaker feature set is also the less stable one, reinforcing Figure 6.4's overfitting finding from a different angle.

**Choice of evaluation metrics.** Accuracy alone was judged insufficient for this classification problem and is reported here only alongside macro-averaged F1-score, precision, and recall. The three target classes (No Fit, Potential Fit, Good Fit) are not evenly represented in real recruitment data — most candidate-job pairs are genuinely poor fits — so a model that simply predicted "No Fit" for every input could score deceptively well on raw accuracy while being useless for the one class (Good Fit) the system actually exists to surface. Macro F1-score weights all three classes equally regardless of how often each occurs, which is why it, rather than accuracy alone, is used as the primary basis for model selection in Table 6.4, and why the per-class breakdown in Table 6.8 and Figure 6.2 is reported explicitly rather than only the aggregate figure.

**User acceptance / usability testing** (candidates, employers, and academic evaluators reviewing screen flows and match explanations) was identified in Section 3.4 as a fact-collection mechanism appropriate to the human-centred requirements in Table 4.6 (NFR-06 in particular), but was not the empirical focus of this chapter; it is recorded as a required activity ahead of final submission rather than claimed here as completed, since it depends on a deployed instance of the system being available to sample users.

**Load/performance testing** against NFR-01 and NFR-10 was scoped out of this evaluation cycle for the same reason — it requires a deployed instance under realistic concurrent load, which was outside the boundary of this thesis's evaluation window — and is likewise recorded as a follow-up activity in Section 7.5.

# 6.5 Chapter Summary

This chapter evaluated IRAS through three complementary layers of evidence: a design-time functional and non-functional test plan tracing ten representative test cases to specific requirements and implementation units; an attempted execution of the existing xUnit suite, which surfaced a genuine, currently open compile-time defect in the test fakes rather than a false-positive green build; and a complete, empirical evaluation of the trained candidate-job fit classifier — full per-class classification reports, confusion matrices, ROC/precision-recall curves, learning curves, and a validation-versus-holdout reliability check — which together showed that combining structured skill-overlap and semantic-similarity features with free text improves test accuracy by roughly 25 to 44 percentage points over text alone, that the accuracy gap is a feature-quality ceiling rather than a data-quantity shortfall, and that a cross-platform model-serialization failure initially forced a deployment-reliability trade-off in favour of Logistic Regression over the higher-scoring XGBoost, a trade-off subsequently resolved by exporting the XGBoost booster through its own native, OS-independent format — so the model actually deployed to production is XGBoost, the highest-scoring configuration of the four algorithms compared. Chapter 7 now draws these findings together against the research objectives set out in Chapter 1.
