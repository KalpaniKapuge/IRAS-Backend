#C CHAPTER 05 - IMPLEMENTATION / DESIGNING

# 5.1 Implementation Approach

IRAS was implemented incrementally, sprint by sprint, following the Scrum plan set out in Section 3.6. Each sprint targeted one vertical slice of the system — a database migration, the corresponding domain entities, the application-layer service, the API controller, and (where relevant) the AI-service integration — rather than building every layer of the whole system at once. This section elaborates the algorithmic logic behind the system's most significant contribution, the multi-signal scoring pipeline, before covering the AI-assisted skill-gap and evidence-review logic, the technology choices made, and the implementation of the platform's most significant AI-driven features.

## 5.1.1 Algorithms

The core of IRAS's contribution is a scoring algorithm that never depends on a single signal. Four algorithms are described below in pseudocode form, each corresponding to a method that exists in the implemented ScoringService and JobMatchingService.

**Algorithm 1 — Taxonomy-based Skill Match**

CODE:
function ComputeSkillMatch(requiredSkills, candidateSkillIds):
    if requiredSkills is empty:
        return 1.0                          // no requirement -> full match
    totalWeight = sum(rs.Weight for rs in requiredSkills)
    if totalWeight <= 0:
        return 0.0
    matchedWeight = sum(rs.Weight for rs in requiredSkills
                         if rs.SkillId in candidateSkillIds)
    return round(matchedWeight / totalWeight, 4)
ENDCODE

Each required skill on a job carries a weight (MustHave skills outweigh NiceToHave skills), so a candidate missing one optional skill is scored more favourably than one missing a mandatory skill — a distinction a pure keyword match cannot express.

**Algorithm 2 — Weighted Total Score**

CODE:
function ComputeTotalScore(skillMatch, semanticSimilarity, mlFitScore = null, assessmentScore = null):
    score = SkillMatchWeight * skillMatch + SemanticSimilarityWeight * semanticSimilarity
    if mlFitScore is not null:
        score += MlFitScoreWeight * mlFitScore
    if assessmentScore is not null:
        score += AssessmentScoreWeight * assessmentScore
    return round(score, 4)
ENDCODE

The weights are read from configuration (ScoringOptions) rather than hard-coded, so the platform operator can shift emphasis — for example, enabling MlFitScoreWeight once the trained classifier described in Chapter 6 is deployed — without a code change or redeploy.

FIG:scoring_pipeline.png|Figure 5.1|Weighted Scoring Pipeline. The block diagram shows the four independent signals — skill match, semantic similarity, ML fit score, and assessment score — feeding into a single configurable weighted sum, which is then persisted as the Application's or JobMatch's headline score and compared against the auto-match threshold; the asterisked note records that the ML fit-score and assessment-score weights default to zero so existing deployments are unaffected until an operator opts in, even though both signals are still computed and stored.

**Algorithm 3 — Batched Proactive Matching**

CODE:
function RunMatchingForJobAsync(jobId):
    job = LoadPublishedJob(jobId)
    alreadyConsidered = JobMatches where JobId = jobId  -> candidateIds
    eligible = CandidateProfiles where OptInMatching = true
               and CandidateId not in alreadyConsidered
               and has a parsed primary resume
    if eligible is empty: return

    // one batched HTTP call for every eligible candidate against this job,
    // not one call per candidate
    signals = ScoringService.ComputeMatchSignalsAsync(job, eligible)

    for candidate in eligible:
        skillMatch = ComputeSkillMatch(job.RequiredSkills, candidate.SkillIds)
        (semanticSimilarity, mlFitScore) = signals[candidate.Id]
        totalScore = ComputeTotalScore(skillMatch, semanticSimilarity, mlFitScore)
        passed = totalScore >= AutoMatchThreshold
        save JobMatch(jobId, candidate.Id, totalScore, passed)
        if passed: NotifyCandidate(candidate.Id, job)
ENDCODE

This algorithm is deliberately batched: the naive design would call the AI service once per eligible candidate, which does not scale once a job has hundreds of opted-in candidates to consider. Batching the resumes and job text into a single request to the AI service's ranking endpoint keeps the number of outbound HTTP calls constant with respect to job count rather than linear in candidate count.

**Algorithm 4 — Confidence-gated Evidence Review**

CODE:
function SubmitEvidenceForReviewAsync(evidenceId):
    SetStatus(evidenceId, Pending)
    (recommendation, confidence) = AiEvidenceReviewer.Review(evidence, planStep)
    if confidence >= AutoApproveThreshold:
        ApplyDecision(evidenceId, recommendation, source = "AI")
    else:
        QueueForAdminReview(evidenceId, recommendation, confidence)
ENDCODE

Evidence review is not fully automated: only high-confidence AI recommendations are applied directly, and every AI decision — whether auto-applied or queued — is written to the audit log with its confidence value, satisfying NFR-09 and directly addressing the transparency concern raised in Section 4.2.

### 5.1.3.1 Programming Language

The backend is implemented in C# targeting .NET, chosen for its static typing, mature async/await support (essential given the number of outbound AI-service calls on the request path), and first-class integration with Entity Framework Core. The AI microservice is implemented in Python, the de facto language for the NLP and machine-learning libraries the ranking and parsing features depend on. The frontend is implemented in TypeScript, chosen over plain JavaScript so that the shape of API request/response DTOs is checked at compile time rather than discovered at runtime.

### 5.1.3.3 Backend and Frontend Frameworks

The backend follows the layered ASP.NET Core Web API convention described in Section 4.5 (IRAS.API, IRAS.Application, IRAS.Domain, IRAS.Infrastructure as four separate projects referenced in that dependency direction only, enforced by the .csproj references themselves). The frontend is a Vite-built single-page React application that consumes the Web API over HTTPS and renders three distinct route trees for the Candidate, Employer, and Admin roles, gated by the JWT claim carrying the user's role.

# 5.2 Significant Implementation Features

This section elaborates the implementation of the features that carry IRAS's actual research contribution, rather than routine CRUD screens such as login or profile editing, which follow standard ASP.NET Core Identity-style patterns and are not separately discussed here.

**AI-assisted job description generation.** The employer job-posting workflow (FR-11) uses a two-implementation pattern behind a single IJdGenerator interface: a GeminiJdGenerator that calls the configured LLM with the employer's minimal input (title, seniority, required skills, work arrangement) and a TemplateJdGenerator that assembles a structured description from a fixed template when no LLM key is configured or the call fails. The controller always returns the generated draft as editable text rather than publishing it directly — the employer must explicitly approve it, which is the human-in-the-loop control called for in Section 3.6.2's Human Oversight mitigation.

CODE:
async function GenerateJobDescriptionAsync(request):
    try:
        draft = await GeminiJdGenerator.Generate(request)
    catch (AiServiceException):
        draft = TemplateJdGenerator.Generate(request)   // deterministic fallback
    return DraftJobDescriptionDto(draft, source: draft.Source, requiresApproval: true)
ENDCODE

**Multi-signal candidate ranking.** Described algorithmically in Section 5.1.1; the implementation detail worth highlighting here is that ComputeSkillMatch runs entirely inside the .NET process against the locally cached skill taxonomy, while semantic similarity and the fit-classifier score are the only two values that cross the network boundary to the AI service — keeping the latency-sensitive, purely-relational part of the score computation local, and only paying the network cost for the two signals that genuinely require it.

**Skill-gap explanation and improvement-plan generation.** When an application or profile comparison reveals a skill gap, SkillGapService first computes the gap set deterministically (required skills minus candidate skills, by weight), then passes that gap set — not the raw resume — to an IGap Explainer (Gemini-backed, with a template fallback identical in shape to the JD generator) to produce a plain-language explanation. SkillImprovementPlanService then sequences the gap into an ordered plan of SkillPlanStep records with a target proficiency level and priority, which the candidate works through and submits SkillPlanEvidence against.

**Confidence-gated evidence review.** Described algorithmically as Algorithm 4; the implementation detail is that the AI evidence reviewer's confidence score is persisted alongside its recommendation even when an administrator later overrides it, so the audit log can show not just what decision was made but how confident the AI was when it made (or failed to make) that decision autonomously.

**Role-aware chatbot.** ChatService delegates context construction to one of three ContextBuilder implementations — CandidateChatContextBuilder, EmployerChatContextBuilder, or AdminChatContextBuilder — selected by the authenticated user's role, so that the LLM prompt is only ever populated with data that role is authorized to see. A ChatScopeGate then filters the LLM's response before it reaches the user, rejecting answers that stray outside recruitment-relevant topics, which implements the "Chatbot Misuse" mitigation from Table 3.2.

CODE:
function BuildAndSendPrompt(user, message):
    contextBuilder = SelectContextBuilder(user.Role)     // Candidate | Employer | Admin
    context = contextBuilder.Build(user)                 // only this role's own data
    reply = ChatResponder.Respond(context, message)       // Gemini, or rule-based fallback
    if not ChatScopeGate.IsInScope(reply):
        return FallbackReply("I can only help with recruitment-related questions.")
    return reply
ENDCODE

**Resume parsing.** CvService streams the uploaded file to the AI service's /parse-resume endpoint together with the current skill taxonomy, receives back parsed text, detected skills (each tagged with how it was matched — exact alias or learned-from-parsing), emails, phones, and a word count, and persists a Resume and a set of CandidateSkill rows tagged SkillSource.ResumeParsed. The candidate is always shown this extraction as an editable preview before it is treated as authoritative, consistent with the parsing-accuracy limitation noted in Section 2.5.1.

**Error handling and logging strategy.** Every outbound call to the AI service is wrapped so that a timeout, a non-2xx response, or a malformed payload is caught at the AiServiceClient boundary and converted into a typed result object (for example, RankResult.Success = false with an Error message) rather than allowed to propagate as an unhandled exception up through the Application and API layers. This choice was made deliberately after observing, during early integration testing, that an unguarded call would otherwise turn a single slow or unavailable AI-service instance into a cascading 500 error for every candidate awaiting a score, which is precisely the fragility NFR-03 was written to rule out. A central ApiExceptionFilter additionally converts any remaining unhandled exception into a structured JSON error response rather than a raw stack trace, and every AI-service failure, admin action, and evidence-review decision is written through a shared logging path so that Section 6.3's audit-trail evidence and Chapter 4's NFR-09 requirement are backed by the same underlying mechanism rather than two separate, potentially inconsistent implementations.

# 5.4 Chapter Summary

This chapter detailed how the research design from Chapter 4 was implemented: the weighted, multi-signal scoring algorithms that form the system's central contribution; the technology choices behind the .NET backend, the Python AI service, and the React frontend, each justified against the alternatives considered; and the implementation of the platform's most significant AI-driven features — job description generation, candidate ranking, skill-gap explanation, evidence review, the role-aware chatbot, and resume parsing — each built with a human-in-the-loop or confidence-gated control point rather than as an unsupervised automatic decision-maker.
